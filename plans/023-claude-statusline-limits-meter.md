# Plan 023: Claude Code statusLine rate-limit meter

> **Status: CANDIDATE — planning only.** Drafted 2026-09-14 against the accepted `main` baseline at `2a4c481`, with file:line citations checked against the current `fix/descope-auto-reconciliation` checkout at `2e1117b`. `PHASE 32 ACCEPTED` is recorded; this is new scope and needs its own explicit approval before implementation, independent of unaccepted Phase 33 work on this branch. Recheck changed files against the chosen accepted baseline before building. Companion to `docs/IDEAS.md`'s "Claude Code model and account-limit meters in the project sidebar — build brief" (Compass study section) — that brief supersedes an earlier, incorrect conclusion in the same file that no live rate-limit source exists for Claude Code; this plan implements the corrected finding (Claude Code's `statusLine` JSON, not local token summation).

## 1. Outcome and boundary

Give the person running a Claude Code tab the same at-a-glance answer the Codex meter targets (`docs/IDEAS.md`'s Codex build brief, not yet promoted to its own plan): is the shared Claude.ai account allowance close to exhausted, without leaving Logic Loop or Claude Code's own interactive UI. Source is Claude Code CLI v2.1.251+'s documented `statusLine` mechanism: the CLI runs a user-configured `statusLine.command`, feeds it a JSON object on stdin including `rate_limits.five_hour.{used_percentage,resets_at}` and `rate_limits.seven_day.{used_percentage,resets_at}` (present only for Pro/Max subscribers or gateway spend-limit accounts, and only after the session's first API response), and renders whatever the command prints to stdout as the terminal's status line.

Chosen shape, decided 2026-09-14 for parity with the Codex brief's app-owns-the-read-path architecture (a copy-paste-snippet alternative was considered and rejected — see `docs/IDEAS.md`): Logic Loop detects an **existing** `statusLine.command` in the user's Claude settings and installs a thin wrapper that (a) execs the original command unchanged so the visible status line stays byte-identical, and (b) separately, non-blockingly, mirrors the same stdin JSON to Logic Loop's local ingest server. First release requires an existing `statusLine.command` to wrap — a user with none configured sees an explicit "No status line configured — nothing to connect" state, not an auto-created one; creating a statusLine from scratch for such a user is explicitly out of scope for this plan (adds an unbounded design surface — default format, `padding`, `refreshInterval` choices — nobody has asked for). In the bound, active Claude tab's expanded `SidePanel`, add a small "Claude usage" block: model name (already available for free from the transcript tailer, no wrapper needed) plus, when the wrapper is enabled and data has arrived, two bars — "Claude · 5h" and "Claude · weekly" — with used percentage and reset time. No cost, no dollar figures, no cross-tab/cross-project attribution beyond "shared across this account," no account switching, no auto-creating a statusLine for a user who has none, no terminal input, no change to what Claude Code itself renders in the terminal.

Independent of the Codex meter (different source, different install mechanism, no shared code beyond the ingest server's auth/transport). Independent of candidate Plan 022 (`v_requests_v2` is a Safe Router concern; this never touches that database).

## 2. Current-code decision record

- **Existing hook-install pattern does not directly apply — different JSON shape.** `src-tauri/src/ingest.rs`'s `apply_setup`/`strip_ours` (ingest.rs:353-374, :341-351) manage `~/.claude/settings.json`'s `hooks.<Event>` keys, each an **array** of `{hooks:[{type,command}], matcher?}` entries; `is_ours` (ingest.rs:315-322) detects Logic-Loop-owned entries via `MARKER` (ingest.rs:9) embedded in the command string, and the array-retain idiom is what makes `strip_ours` restore the original byte-for-byte. `statusLine` is a **singleton object** `{type:"command", command:"..."}`, not an array — there is nothing to filter/retain. This plan adds new, parallel logic in a new `src-tauri/src/statusline.rs`: detect an existing `statusLine.command`, save it verbatim, swap in the wrapper's command, and on removal write the saved value back — a single-key swap-and-restore, not a list merge. `read_settings`/`write_settings` (ingest.rs:324-339, whole-blob read-modify-write, pretty-printed with trailing newline) are reused as-is; everything downstream of them is new.
- **No existing "wrap a foreign command transparently" pattern.** Confirmed by reviewing `src-tauri/src/codex.rs`'s parallel hook installer (codex.rs:30-98): it manages `~/.codex/hooks.json`, a file Codex auto-discovers that happens to be Logic-Loop-owned in practice, but the code is still a full read-merge-write of Logic-Loop's *own* entries — it never preserves and execs a third party's pre-existing command. The statusLine wrapper (exec-through original + side-channel mirror) is new for this codebase, not a reuse.
- **Original-command storage lives inside the generated wrapper script, not a separate state file.** The wrapper is written to a fixed path (`~/.context-terminal/claude-statusline-wrapper.sh`), and the original `statusLine.command` string is baked into that script as a literal at write time (e.g. a `ORIGINAL_COMMAND='...'` line), not a second side-file that could drift out of sync with `settings.json`. `settings.json`'s `statusLine.command` field points at the wrapper path; the wrapper is the single source of truth for "what to restore." Detecting "already ours" reads a `MARKER`-style comment on the wrapper script's first line (reusing the existing `ingest.rs:9` constant) rather than scanning JSON, since the thing being marked is a file, not a JSON string.
- **Stdin can only be read once — the wrapper must buffer it.** The wrapper reads Claude Code's JSON off stdin into a variable, execs the original command with that same buffered input to produce the visible status line (so the original command still behaves exactly as before — including scripts that shell out or check other stdin-adjacent state), and separately, in a **backgrounded, non-blocking** subshell, POSTs the same buffered JSON (or just the `rate_limits`+`model`+`session_id`+`workspace` slice) to the ingest server. The mirror POST must never delay the visible status-line render — it follows the existing hook curl's fail-open shape (`ingest.rs:289-296`: `-sf -m 2`, discarded output, no dependency on the exit code) but additionally must be backgrounded (`( curl ... & )`) since, unlike a hook, this command's stdout is rendered live in the terminal on every keystroke-adjacent update.
- **New ingest transport, not a reuse of `/event`.** `POST /event` (ingest.rs:97-127) is hook-shaped: it derives `project_key` from a top-level `cwd` field, and the frontend's `onHookEvent` (ingest.ts:69-75) gates on `hook_event_name`+`session_id` both being present strings before forwarding to any handler, which in turn (per the existing dedupe design documented in this repo's landmines) is built around `addEvent`'s `events`-table insert and its `tool_use_id`/session+bucket dedupe key. statusLine data is a live gauge that reruns on every assistant message, `/compact`, and idle-timer ticks — routing it through `addEvent`'s per-event persistence would spam the `events` table with a payload shape dedupe wasn't designed for. Add a new endpoint `POST /statusline` on the same `tiny_http` server (same bearer-token check, ingest.rs:72-81, reused verbatim) that emits a distinct Tauri event `ingest://statusline` carrying `{tab_id, project_key, session_id, model, rate_limits}` and is **never** written to the `events` table — kept as transient in-memory state only, mirroring the Codex brief's own "keep account snapshots in transient app state first, no migration needed." `project_key` derivation reuses `pty::project_key` the same way `/event` already does (ingest.rs:107-116), reading the JSON's `workspace.current_dir` field instead of `/event`'s top-level `cwd`. Binding to a tab reuses `bindSession`'s existing tether-first/cwd-fallback logic (ingest.ts:115-144) unchanged — it is payload-shape-agnostic and only needs `tab_id`/`project_key` supplied the same way `/event` already supplies them.
- **Tether is inherited correctly with no new stamping needed.** `EXTRACTOR_TETHER` (ingest.rs:16) exists to stop Logic-Loop's own directly-spawned `claude -p` extractor children from self-ingesting (extractor.rs:230/:253 stamp it because those children are spawned outside any PTY shell). A Claude Code session's statusLine wrapper is the reverse spawn direction: it runs as a grandchild of a Logic-Loop-spawned PTY shell (`pty::pty_spawn`, pty.rs:204-240 sets real `LOGIC_LOOP_TAB_ID` on the shell env, pty.rs:240), and every child process in that tree — the `claude` CLI, and in turn its `statusLine.command` subprocess — inherits that real tab id through normal process-tree env inheritance, exactly like the existing hook commands already do. No `EXTRACTOR_TETHER`-style stamp applies here; the wrapper just reads whatever `$LOGIC_LOOP_TAB_ID` is already in its environment, same as `hook_command_with_agent` (ingest.rs:289-296) does today. A Claude Code session started outside any Logic Loop tab (a separate Terminal.app window with the wrapper still installed globally) carries no tether at all — handled by the existing absent-tether/cwd-fallback path (ingest.ts:127-143), not a new problem.
- **Settings key: schemaless, no migration.** `ExtractorSettings` (`src/types.ts:142-148`, persisted via `src/lib/repo.ts:719-754`'s generic `settings` key/value table with no dedicated migration) is the precedent: add one new key, e.g. `claude_statusline_wrapper_enabled`, to that same table. Check `LandingNoteMode`'s (`types.ts:140`) getter/setter for the exact string convention this table uses for a small enum/flag before picking `"true"/"false"` vs `"1"/"0"`, to stay consistent with existing fields rather than introducing a third convention.
- **UI placement.** `SidePanel.tsx`'s pinned header stack: project/session heading (906-943), then `<SidebarLmControl />` + mute toggle row (944-972), then `adapterWarnings`/blind-path warning strips (973-1012+). The new "Claude usage" block is its own row inserted between the SidebarLmControl row and the warning strips (i.e. after line ~972, before ~973) — matches the stacked-strip convention already there and the IDEAS brief's stated placement ("below the project/session heading, before event sections"). The block shows only for the active, bound, Claude-agent tab, mirroring the Codex brief's "no meter for an unbound tab or an agent whose marker is not [this agent]."
- **Opt-in confirmation UX, not the pre-approved hook-toggle exception.** `AgentStatusBar.tsx`'s `ADAPTER_ACTIONS`/`toggleAdapter` (AgentStatusBar.tsx:40-137) is a one-click, no-confirmation toggle — this is the "hook entries via the app's own toggle" path CLAUDE.md pre-approves, and it does not extend to `statusLine` (a different settings key, with real clobber risk against a command the user wrote by hand). The closer precedent is the Commit & Push footer's untracked-files amber box (`SidePanel.tsx:1686-1703`): a labeled, unchecked-by-default opt-in that states plainly what will happen before any write. The new "Claude usage" block, when no wrapper is installed yet, shows a quiet inline enable action with the same shape: state the detected existing `statusLine.command` verbatim, explain it will be wrapped (original preserved, restorable), and require an explicit click — never auto-enable on session bind.

## 3. UI states and refresh

1. States for the "Claude usage" block, matching the IDEAS brief's states-and-proof list: `not-offered` (agent isn't Claude, or tab unbound — block doesn't render at all), `wrapper-not-installed` (show the enable action described above), `wrapper-installed-loading` (session started, first response not yet seen — `rate_limits` legitimately absent), `unavailable-ineligible` (CLI ≥ v2.1.251 confirmed but no `rate_limits` — non-Pro/Max account), `unavailable-old-cli` (CLI < v2.1.251 — same missing-field signature as ineligible, disambiguated only by a separate `claude --version` check, matching the IDEAS brief's explicit call-out that "field missing" collapses two causes), `available` (bars render), `stale` (no update received since a cadence event was expected — label last-good data as stale, never silently freeze it as current), and the `spend_limit` over-100 case (clamp the bar's fill, not the displayed percentage number). Model name renders independently of all of the above, from the existing transcript tailer, so it's visible even in `wrapper-not-installed`.
2. Reset time renders in the user's local timezone from `resets_at` (unix epoch seconds) — never manufacture a reset time when the field is absent. Never join or sum values across tabs/projects; each is a single account-wide number that happens to be currently visible because this tab is bound and active, same non-summing rule the Codex brief states explicitly.
3. Update cadence is push-driven, not polled: the wrapper's mirror POST fires whenever Claude Code itself reruns the statusLine command (session start/resume, new assistant message, `/compact`, permission-mode change, vim toggle, an optional `refreshInterval` floor, and automatically again the moment a previously-seen `resets_at` is reached — see `docs/IDEAS.md`'s cadence note). `src/App.tsx` listens for `ingest://statusline`, keeps the latest snapshot per `tab_id` in React state (or a small module-level map), generation-guarded the same way other tab-scoped listeners already are for StrictMode double-mount, and does **not** persist it to SQLite — it's live gauge state, not an append-only fact. A stale flag is set client-side if no update lands within a bounded window after a cadence event that should have produced one (e.g. no update within N seconds of a new assistant-message hook event for the same session) — exact threshold decided during implementation, documented in the plan's test section once chosen.

## 4. Wrapper install/uninstall mechanics — the risky part, spec it precisely

1. **Setup.** Read `~/.claude/settings.json`. If `statusLine` is absent or has no non-empty `command`, surface `wrapper-not-installed` with the "no status line configured" copy — do not offer to create one this release. If `statusLine.command` already equals the wrapper's fixed path *and* the wrapper file at that path carries the `MARKER` comment, treat as already installed (idempotent no-op — re-running setup regenerates the wrapper file from its own already-embedded original, in case the wrapper's template changed between Logic Loop versions, without re-reading `settings.json`'s `command` field, which by now IS the wrapper path, not the real original). Otherwise: write the wrapper script to `~/.context-terminal/claude-statusline-wrapper.sh` (mode `0700`, same directory Logic Loop already owns for `ingest.env`, ingest.rs:58-63) embedding the *current* `statusLine.command` value as the literal original, then rewrite `settings.json`'s `statusLine.command` to the wrapper's path (leave `type`, `padding`, `refreshInterval`, and every other key in the `statusLine` object and the rest of the file untouched — whole-blob read-modify-write, same as `write_settings`).
2. **Remove.** If `statusLine.command` doesn't point at the wrapper path, this Logic Loop instance doesn't own the current statusLine — no-op, don't delete a stray leftover wrapper file blindly (guards against a second Logic Loop install, or the user having manually repointed `statusLine` since). Otherwise: read the wrapper file's embedded original command, write it back into `settings.json`'s `statusLine.command` verbatim, delete the wrapper script file. Byte-for-byte restore of the pre-setup file is the bar, matching this repo's existing standard for `~/.claude/settings.json` writes (CLAUDE.md's landmine: "writes must stay idempotent and byte-identical reversible").
3. **Status check.** A cheap read-only command reports `installed`/`not-installed`/`foreign` (statusLine exists and isn't ours) for the enable-action UI to pick the right copy, mirroring `hooks_status`'s shape (ingest.rs:422-433) but against the new singleton-swap state instead of the array `.any(is_ours)` check.
4. **Version gate.** Before offering the enable action at all, confirm the installed Claude Code CLI is ≥ v2.1.251 (a version check, likely extending whatever `claudeDetect()` already probes per `AgentStatusBar.tsx`'s `ADAPTER_ACTIONS` — exact mechanism to confirm during implementation since the research pass for this plan didn't inspect `claudeDetect()`'s internals). Below that version, show `unavailable-old-cli` and do not offer to install the wrapper at all — installing it against an old CLI would just wrap a command whose stdin JSON never carries `rate_limits`.

## 6. Verification and failure cases

Focused Rust tests, all against temporary `settings.json`/wrapper-script fixtures, never a live `~/.claude/settings.json`: no existing `statusLine` → `wrapper-not-installed`, never creates one; existing foreign `statusLine.command` → setup wraps it, second setup call is a no-op producing byte-identical `settings.json`, remove restores the exact original string; `statusLine.command` pointing elsewhere (not our wrapper) → remove is a no-op, doesn't delete files; a wrapper file present but `settings.json` repointed away from it by the user → treated as foreign, not force-restored; malformed/missing `~/.claude/settings.json` → same `{}`-default behavior `read_settings` already has; every other key in `settings.json` (including unrelated `statusLine.padding`/`refreshInterval` and the existing `hooks.*` block) survives setup+remove untouched. Focused TypeScript checks cover every state in §3 rendering distinct copy, real `0%` vs. absent-field "loading" not being conflated, `spend_limit` over-100 clamped visually but not numerically, stale-detection after a simulated cadence-event-with-no-update, and per-tab isolation (two Claude tabs never cross-contaminate snapshots).
